    5. Release¶

    Publish Python packages to GitHub Releases and documentation to GitHub Pages.

    Automatic release¶

    Merge a releasable change to dev for a release candidate, or promote dev to main for a stable release. release.yml validates the source, versions and builds every package, then uploads artifacts. A tagged stable release also deploys docs from that tag. Docs-only commits do not publish docs. Versions come from Conventional Commits; never edit versions or create tags manually.

    By hand¶

    Use a clean main (stable) or dev (prerelease), synchronized with origin. Complete setup and GitHub login, then run:

    make check
make release

    The release command versions, builds and uploads the full wheel/sdist set. It changes Git and GitHub; coding agents need explicit per-action approval. Local publication also asks you to type yes. For a stable manual release, publish docs separately from the clean released tag:

    make deploy-doc-gh

    That command pushes gh-pages and requires separate authorization.

    Retry an interrupted release¶

    Retry the failed CI job if its tested source still matches the release. Locally, rerun make release on the matching clean release branch. To upload from a clean checkout of the exact release tag:

    make build-package
make release-assets

    If newer application commits exist, let their own workflow validate/release them. Never rebuild an older release from later source. release-assets can create a missing GitHub release and replaces same-named attachments (--clobber); it does not publish to a package index.

    Credentials¶

    gh auth login

    Credentials resolve from GH_TOKEN (environment or local .env), then the token saved by gh auth login, then a hidden terminal prompt. release-assets uses the token or gh login. CI supplies its automatic GitHub token; never print credentials. A tooling-only environment can use make install-release; docs need make install-tools or make install-dev.

    Release sequence and safeguards¶

    Target / stage Behavior
    make release-version Require main/dev, a clean tree and HEAD equal to fetched origin
    Semantic-release build hook uv lock && git add uv.lock && make build-package; build failure stops commit/tag/publication
    make release-assets Require the tag at HEAD and one wheel/sdist per PACKAGE_PROJECTS entry
    make release Run versioning, reuse valid artifacts or build missing ones, then upload sequentially

    All workspace package versions equal the root version. Tags retain vX.Y.Z-rc.N spelling; Python artifacts use normalized X.Y.ZrcN filenames. CI retries may accept the exact tagged, single-parent chore(release): v<version> [skip ci] child of the tested source; newer application changes require validation. Git hooks are disabled only during semantic-release. With no new version or matching tag at HEAD, make release stops without uploading.

    Repository settings (once)¶

    Enable Actions release write permissions and configure Pages to deploy from gh-pages. Enable squash merging so PR titles determine versions. CI installs tools with --locked using install-tools, install-release or install-dev according to the job.

    After a release: sync main into dev¶

    Merge main back into dev after a stable release. Use the stable version/changelog as the base for the next candidate; see branch conventions.
