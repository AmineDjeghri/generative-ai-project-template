# 3. Conventions

The rules every change follows.

## Code

- Use the `make` targets (`make help`): CI runs the same ones.
- Settings come from `backend_settings.py` / `frontend_settings.py` (pydantic-settings, `.env`),
  never `os.environ` scattered in the code. Secrets are `SecretStr`.
- Logging: the loguru `logger` from the settings module (colored, level `LOGGING_LEVEL`):

    ```python
    from genai_template_backend.backend_settings import logger

    logger.info(f"Loaded {count} documents")
    ```

- Log the error, then raise it; skip the raise only when the loop must go on:

    ```python
    except Exception as e:
        logger.error(e)
        raise
    ```

- Prefer an `if` check over catching and re-raising when you can (log, then raise).
- Large data: Polars. CPU-bound work: `multiprocessing` pool map. I/O: `asyncio`.

## Branches and pull requests

1. Comment on (or create) the issue and wait to be assigned.
2. Branch off `dev`: `feature/<name>` or `bugfix/<name>`. Stay up to date with `git merge dev`
   (branch already pushed) or `git rebase dev` (local only).
3. Open a pull request to `dev`; its **title** follows the commit convention below: it becomes the
   squash commit and decides the version.
4. When `dev` is ready, a pull request `dev` → `main` releases it.
5. After a release, merge `main` back into `dev` (merge commit, direct push). On conflicts on
   `CHANGELOG.md` or a `pyproject.toml` version, keep `main`'s.

| Merge                 | Strategy                  | Why                                                      |
|-----------------------|---------------------------|----------------------------------------------------------|
| `feature/*` → `dev`   | squash                    | one conventional commit per feature                      |
| `dev` → `main`        | squash                    | one commit for semantic-release to evaluate              |
| `main` → `dev` (sync) | merge commit, direct push | `[skip ci]` in the release commit prevents a spurious RC |

Never edit a version in `pyproject.toml` or create a tag by hand: semantic-release does both.

## Commit convention

`[emoji] <type>[(<scope>)][!]: <description>`, the emoji is optional ([Gitmoji](https://gitmoji.dev/)).

| Emoji                | Type                                                        | Aliases                   | Release |
|----------------------|-------------------------------------------------------------|---------------------------|---------|
| 🐛                   | `fix`                                                       | `bugfix`, `hotfix`        | patch   |
| ⚡️                   | `perf`                                                      |                           | patch   |
| ✨                   | `feat`                                                      | `feature`                 | minor   |
| 💥                   | `feat!`                                                     | `BREAKING CHANGE:` footer | major   |
| ♻️ 📝 🎨 🧪 🔧 👷 📦 | `refactor`, `docs`, `style`, `test`, `chore`, `ci`, `build` |                           | none    |

A `!` or `BREAKING CHANGE:` footer makes any allowed type a breaking change (major release).

```text
✨ feat(auth): add GitHub App token rotation
🐛 fix(llm): handle empty response from the API
💥 feat!(api): remove the v1 endpoint

feat(auth): redesign token flow

BREAKING CHANGE: /v1/token removed, use /v2/auth instead
```

On `dev`, a releasable commit increments the RC counter (`1.1.0-rc.1` → `1.1.0-rc.2`)
unless a larger version bump is needed (for example, a breaking change → `2.0.0-rc.1`
when the last stable release was `1.0.0`).

Scopes are optional. Common scopes: `llm`, `api`, `frontend`, `backend`, `ci`, `deps`. The commit message is checked on
commit (commitizen) and the pull request title by `ci.yml`.

## Secrets

- Never commit a credential: use environment variables or `.env` (git-ignored).
- `detect-secrets` runs on commit. For a line that intentionally references a secret placeholder (`${{ secrets.X }}`),
  add `# pragma: allowlist secret`. File-level exclusions in
  `.pre-commit-config.yaml` only for recurring false positives; never exclude a whole workflow to
  silence one line.

## Environment variables

Adding, renaming or removing one, in the same change: the setting in `backend_settings.py` or `frontend_settings.py`,
`.env.example`, and the workflow `env:` if CI needs it.

## Dependencies (Renovate)

Renovate (`.github/renovate.json`) opens pull requests with the `renovate` and `dependencies` labels; most routine
updates have a 7-day cooldown; security fixes are not grouped and open at once. Renovate pins runtime dependencies, including existing ranges;
`uv.lock` makes builds reproducible. Review every Renovate pull request; a dependency dashboard
issue lists the pending ones.

1. CI runs `make test-all` on Python 3.14.8 only.
2. Renovate does not widen the Python range. The supported interpreter moves by hand, together with
   the CI job, the Docker base image and this document; Python Docker updates have a separate `python runtime`
   group and require dependency dashboard approval, so review the interpreter before merging.
3. PyPI updates use strict Python compatibility filtering. Weekly lockfile maintenance refreshes
   versions already permitted by dependency ranges; review the lockfile and CI results too.
4. Renovate updates dependency files, GitHub Actions and pre-commit revisions; update README
   and developer documentation when the supported Python range changes. Docs are not rewritten
   automatically.
5. Renovate tracks the Node pin used by pre-commit. Stable updates wait seven days and use
   `chore`; major upgrades require dependency dashboard approval.
