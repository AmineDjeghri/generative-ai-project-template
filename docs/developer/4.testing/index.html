    4. Testing¶

    make test-all is the required comprehensive software check for users, developers and GitHub Actions. Run it before reporting that the software is fully validated. It runs the self-contained suites first, then real-service integration tests where a suite exists. make test-local remains a focused diagnostic shortcut; passing it does not establish full validation. The ambiguous make test target is removed.

    Keep static quality, coverage reporting and artifact/runtime checks explicit alongside software tests. make check combines static checks, make test-all and strict documentation validation. It can call real services. make help lists focused commands and their requirements.

    The comprehensive command does not accept per-suite ARGS filters; use focused targets for selected tests. Worker-count options remain available.

    Test layout¶

    Folder Purpose
    tests/unit/backend/ Settings, LLM logic and isolated API checks
    tests/unit/frontend/ NiceGUI component and page simulations
    tests/unit/tooling/ Release, docs, startup and test infrastructure
    tests/integration/ Real LLM, Ollama and API calls; live-service fixtures
    tests/hardware/ Explicit GPU checks
    1. Put self-contained tests under unit/ and live-service tests under integration/.
    2. Keep shared setup in tests/conftest.py; scope live and UI fixtures to their own folders.
    3. Keep existing Make commands; they select the appropriate folders and retain N=4 workers.

    Required checks¶

    1. Run make install-dev.
    2. Start Ollama, install the selected model and configure INFERENCE_BASE_URL, INFERENCE_API_KEY and INFERENCE_DEPLOYMENT_NAME for that real service.
    3. Run make test-all, make pre-commit and make docs-build.
    4. Run artifact/runtime checks separately; make test-hardware-cuda needs the optional CUDA PyTorch install.

    make test-all runs unit tests and NiceGUI component/page simulations, then real LLM, Ollama and API-to-LLM integration tests in parallel (N=4 by default). Endpoint probes run inside fixtures, never at collection. Install the configured model before starting the suite; workers do not download or change models. Plain uv run pytest and make test-local exclude integration/hardware execution; neither is the required comprehensive check. Self-contained tests and collection use synthetic fallback settings.

    Focused command Scope
    make test-unit Settings and isolated logic, parallel
    make test-component NiceGUI simulations without a browser or real backend
    make test-local Unit/component tests only; insufficient for full validation
    make test-integration-check Credential-free collection; no endpoint probes
    make test-integration-llm Real inference client tests
    make test-integration-ollama Parallel Ollama tests; selected model must be installed
    make test-smoke-ollama Bounded chat request; model warmup and connectivity check
    make test-hardware-cuda Explicit CUDA hardware check

    Incomplete integration validation¶

    Integration commands fail when tests fail, no tests execute, or any integration test is skipped or deselected. Missing credentials, unavailable services and failed cleanup therefore cannot become a successful comprehensive check. Collection/compilation alone does not establish connectivity. Report the exact checks executed and list unavailable, skipped or unexecuted checks as incomplete. Never substitute a successful focused suite for the required make test-all result.

    Pytest integration runs print skip reasons and write reports/integration.json and reports/integration.xml. GitHub Actions always adds the comprehensive job outcome to its summary, including when prerequisites fail before tests can start. Coverage is reported by its own command/job.

    When a cloud-only endpoint is selected, Ollama tests are inapplicable and skip; the integration gate reports incomplete validation. Use a configured Ollama service for the comprehensive template check. Provider-specific commands remain useful for focused connectivity checks. Coverage instrumentation is not currently configured; UI simulation does not prove a real browser/container works.

    Integration workers¶

    1. Provision the model once before testing (make download-ollama-models for local Ollama).
    2. Run make test-integration or make test-all; integration uses four workers by default.
    3. Override the count with make test-integration N=2 (also applies to the LLM/Ollama targets).
    4. Use N=0 for serial diagnostics or reduce workers if the endpoint rate-limits requests.

    Generation tests use a 64-token output limit and short prompts. Ollama requests disable optional reasoning so the budget produces an answer. The API integration fixture constructs the real model client with the same limits; it still calls the live service and requires a non-empty response.

    GitHub Actions¶

    The software test job runs Python 3.14.8, the interpreter pinned by requires-python (>=3.14.8,<3.15). It installs that interpreter and runs make test-all.

    CI and the shared release workflow invoke make test-all. The software job installs and starts a dedicated Ollama instance on the hosted runner, stores model data under runner.temp and pulls the selected model before running tests. make test-smoke-ollama warms it with a 16-token chat request, reasoning disabled and a 180-second deadline before parallel execution. INTEGRATION_OLLAMA_MODEL optionally overrides the existing template default qwen3.5:0.8b. CI sets INFERENCE_BASE_URL=http://127.0.0.1:11434, a non-secret local Ollama API-key placeholder and INFERENCE_DEPLOYMENT_NAME=ollama_chat/<model> explicitly. It uses the native chat endpoint and sets the existing INFERENCE_TIMEOUT_SECONDS=180 and CHAT_TIMEOUT_SECONDS=240 settings for CPU inference and queued requests. It does not copy a developer .env or require cloud credentials. The service is stopped even after failure, and its log is included in the integration-results artifact alongside the test reports.

    An unavailable service/model or any skipped integration fails comprehensive validation and is visible in the workflow summary. Pre-commit and the existing Compose/runtime checks remain separate.

    What make pre-commit checks¶

    Use make pre-commit FILES="path/to/file.py path/to/other.md" for a focused change review. The default still checks all tracked files.

    Hook Checks
    pre-commit-hooks large files, TOML/YAML/JSON syntax, end of file, whitespace, merge conflicts, LF line endings, test file names
    ruff, ruff-format lint (docstrings, unused imports) and format
    detect-secrets no credential in a file
    markdownlint-cli2, codespell Markdown style and spelling
    properdocs build --strict the documentation builds, no broken link (on docs/ or properdocs.yml changes)
    uv-lock uv.lock matches the pyproject.toml files
    commitizen (on commit) commit message format

    pip-audit, actionlint, zizmor, bandit and markdown-link-check are present in .pre-commit-config.yaml but commented out.

    Request regression checks¶

    1. Run make test-unit for JSON booleans/nulls, generation options, retries and API errors.
    2. Run make test-component for asynchronous UI requests, malformed replies and duplicate submissions.
    3. Run make test-all for comprehensive validation, including the real configured model.

    Release regression checks¶

    1. Run make test-unit for release guards, prerelease filenames, incomplete artifacts, upload recovery and build failures. Git, GitHub and version commands use isolated test substitutes.
    2. Run make docs-build to verify the API reference for every package.
    3. Run make build-package separately to build and verify the complete wheel/sdist set.
